# Clerk user migration

Status: tooling implemented and tested locally with synthetic identities and an isolated PostgreSQL 16 database. No existing player data has been exported or imported, no live Clerk users have been created, and no deployed database or environment has changed. A live DEV rehearsal is required before production.

Run `python3 tools/clerk_migration.py --help` from the `user` repository. Python 3.10+ and the PostgreSQL `psql` client are required for database modes. There are no extra Python packages, web routes or Spring startup jobs.

## What moves

| Source | Clerk / local result |
| --- | --- |
| Numeric `app_user.id` | Clerk `external_id` as a decimal string; the existing local ID stays unchanged |
| Email | Primary address created explicitly as `reserved` (unverified, usable for sign-in, protected against another user claiming it) |
| Bcrypt digest | Original hash passed as `password_digest`, with `password_hasher: bcrypt`; plaintext passwords are never needed |
| First and last names | Preserved, with surrounding whitespace removed in Clerk; missing names are completed after email verification |
| Clerk user ID returned by import | Written only into the original row's `clerk_user_id` |
| Migration provenance | Private Clerk metadata contains only tool version and a SHA-256 digest of the source identity; it supports recovery after a lost response |
| Games, guesses, reads, reviews, grades, rankings | Stay in the existing database and retain their numeric relationships; not exported to Clerk or rewritten |
| Church | Not selected from the source, included in plans/payloads, put in metadata, or updated; old values remain pending the separate retention review |

`clerk_email_verified_at` remains null when linking an imported user. Backend access requires Clerk to confirm a verified primary email before recording verification. The tool checks that newly created/recovered unlinked accounts still have unverified primary email and a password; it stops rather than accepting automatic verification. It does not bypass legal, restriction or password checks or fabricate consent records.

Clerk's create-user API marks email verified by default. The tool pins API version `2026-08-20` and explicitly sends `email_address_identification_status: ["reserved"]`. Never remove this field to work around an API error. Existing email-only matches, including Google accounts without the correct migration mapping, require manual ownership/mapping review; they are not silently merged or overwritten.

## Read-only plans

Without `--check-clerk`, planning makes no Clerk requests and requires no Clerk key. JSON input is useful for offline/synthetic validation; a database plan reads a repeatable-read, read-only snapshot. Neither mode writes local account records. A report is written atomically with 0600 permissions and refuses to overwrite an existing file.

An offline JSON input is an array of objects with `id`, `email`, `password` (bcrypt digest), `firstname`, `lastname`, and `clerk_user_id` (null if unlinked). Optional `row_token` is generated by the database reader. Extra fields are discarded, never forwarded. Keep any real export private and outside version control. The preferred database mode holds the selected fields in memory rather than producing a credential export file.

```sh
python3 tools/clerk_migration.py plan \
  --input /secure/migration/legacy-users.json \
  --instance-id ins_3LsfpHJyCKRlpV4FFdIBf1krOyY \
  --environment development \
  --report /secure/migration/offline-plan.json
```

Configure libpq's `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER` and credential mechanism in your host terminal or use a named `PGSERVICE`. Do not paste database passwords or Clerk secret keys into chat, command arguments, source or reports. The tool does not load environment files or inspect project secrets. Database statements assume the `public` schema and disable `.psqlrc` startup commands.

For a DEV copy of the source database:

```sh
python3 tools/clerk_migration.py plan \
  --source-db \
  --instance-id ins_3LsfpHJyCKRlpV4FFdIBf1krOyY \
  --environment development \
  --report /secure/migration/dev-source-plan.json
```

Then, with that instance's `CLERK_SECRET_KEY` securely available in the host environment, add `--check-clerk` and choose a fresh report path. This only makes GET requests: it verifies the actual instance/environment and checks external-ID, existing mapping and email collisions. The instance uniquely identifies the target application; it does not create or switch applications.

Reports contain IDs, actions, issue codes, safe remote-error descriptions and counts, plus source/database/target fingerprints. They contain no email addresses, names, hashes, payloads or keys. Exit codes are 0 for a plan without blockers, 2 for row blockers, and 1 for configuration/I/O failures. Missing names are warnings; duplicate IDs/emails/links, malformed emails and unsupported hashes are blockers. Remote outages also block, rather than being treated as an empty Clerk user list.

An offline report is not sufficient to apply. Apply requires a reviewed `--source-db --check-clerk` plan, bound to the same actual database name/server/port, source identity fingerprint and Clerk instance/environment. A connection via a different server address can require a fresh plan even when it reaches the same database.

## Rehearse before production

1. Complete the manual bot-account cleanup and make a recoverable database backup under the existing retention/access policy.
2. Apply only the additive 1.2 schema changes, including the unique Clerk-ID index and webhook guard table. Never run unrelated historical SQL blindly.
3. Use an isolated DEV database copy and the selected Bible Game DEV Clerk instance. Do not run a DEV apply against the production database. Review the actual source database and target in the report.
4. Resolve all plan blockers. Freeze legacy registration, password/profile changes and account administration during the snapshot/import/cutover window; keep writes frozen across retries. A changed source identity invalidates the plan; the per-row database token also catches changes after preflight.
5. Run the GET-only online plan and review it. A subsequent live import creates real accounts and links the database, so obtain explicit approval for the actual DEV or production target before executing it.
6. After DEV import and coordinated activation, manually verify: the existing password works, email remains unverified until a successful code/verified-provider flow, unverified access is denied, Google cannot claim another account, missing names are required, and the same numeric ID and full progress remain. Exercise webhook updates/deletion on an approved disposable test account as well. The synthetic tests cannot prove live Clerk dashboard settings or browser behavior.
7. Resolve the recovery route for people without access to their old inbox, bot-protection settings and the remaining release acceptance journeys before approving production.

## Explicit apply and resumption

The following command is documentation, not something run during implementation. It requires a separate reviewed online database plan and explicit target approval. It writes users to Clerk and mappings to the source database.

```sh
python3 tools/clerk_migration.py apply \
  --plan /secure/migration/dev-online-plan.json \
  --journal /secure/migration/dev-import-journal.json \
  --confirm-instance ins_3LsfpHJyCKRlpV4FFdIBf1krOyY \
  --writes-frozen \
  --bot-cleanup-complete
```

Production additionally requires `--allow-production`, a production-instance plan/key, and a completed DEV acceptance rehearsal. Flags acknowledge completed work; they do not perform bot cleanup, freeze writes or back up the database.

The importer rechecks every row before creating anything, then reconciles each account again before creation. It looks up the stable external ID first. A recoverable remote account must match the local ID, primary email and tool provenance. Email equality alone never authorizes linking. Known linked accounts are validated and skipped without resetting passwords or verification.

The journal records only target, source fingerprint, IDs and progress status. It is private, atomically persisted/fsynced, and guarded by a process lock. It records a create intent before calling Clerk and the returned identity before the database write. If the database mapping fails, rerunning the **same command with the same plan/journal** recovers the already-created identity. Resume accepts the mapping changes made by this import while still rejecting changes to source credentials/profile fields.

POST requests are never blindly retried after an uncertain response. A subsequent run first reconciles by external ID and provenance. If a prior create has no remote match, a recorded identity disappeared, verification is unexpected, or a mapping changed, the importer stops for review instead of recreating an account. Do not delete journals or relax these guards to force a retry. Retain plans/journals only as long as needed under the migration retention policy.

Each database link is transactional and conditional on the original source token, an empty mapping and an empty verification marker. It shares the webhook guard lock, rejects deleted Clerk IDs and changes only `clerk_user_id`. SQL statements contain no passwords, hashes, email addresses, names or church values. Other writers can still make a row fail safely after earlier rows succeeded; this is an incremental import, not one distributed transaction.

A database transaction cannot roll back a created Clerk account. After a partial failure, preserve the journal and fix/reconcile the issue; never automatically delete accounts or wipe mappings. A deployment rollback is a separate decision: once users change passwords or progress in Clerk mode, the old credential store may be stale. Keep the rollback window and data reconciliation plan explicit.

## Verification

Fast, offline checks:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/tests -v
```

To include the PostgreSQL checks, use the official `postgres:16-alpine` Docker image:

```sh
CLERK_MIGRATION_POSTGRES_TEST=1 PYTHONDONTWRITEBYTECODE=1 \
  python3 -m unittest discover -s tools/tests -v
```

The opt-in suite creates a new disposable container with no published ports, network access or host mounts, and removes that container afterward. It never connects to an existing database or Clerk. All 27 tests passed, including SQL rollback on source changes, deleted-ID refusal, apply/resume behavior, credential/history preservation, lost responses, duplicate emails, target mismatch, output privacy and read-only planning.
